# 1\. LLD Scope and Frozen HLD Inputs

The following HLD choices are treated as fixed inputs to this LLD:

- Microservices with a bounded service count: gateway-service, repository-service, governance-service, agent-service, graph-intelligence-service; retrieval co-deployed inside agent-service for V1.
- Java/Spring Boot for gateway, repository and governance services; Python/FastAPI/LangGraph for agent intelligence.
- MongoDB is the operational source of truth.
- Redis is used for cache, rate limiting, request coalescing and short-lived coordination.
- Kafka is the asynchronous event backbone; containerized locally and managed when deployed.
- Neo4j is the graph database and is a rebuildable intelligence projection, not canonical truth.
- GCS stores derived repository artifacts, optional full snapshots, datasets and model artifacts.
- Repository clones are ephemeral; derived artifacts are persisted. Full source archives are optional.
- REST carries commands/queries/HITL decisions; SSE carries long-running progress; REST status endpoints recover after disconnect.
- Technology and role discovery are owned by Graph Intelligence; canonical ontology/taxonomy changes are owned by Governance.
- Gemini is the initial LLM; vLLM/open models are later.

**LLD review decisions now finalized: repository analysis is two-stage (deterministic repository-service analysis followed by automatic bounded classification inside agent-service), and graph context is determining for architecture-review result identity.**

## 1.1 Explicitly deferred beyond this LLD baseline

- Exact authentication provider/product selection.

- vLLM model choice, fine-tuning hyperparameters and RLHF/DPO experimental design.
- True multi-region deployment and cross-region replication.

## 2.2 Version identity and freshness

```
DeterministicAnalysisKey =
    repository_key
  + commit_sha
  + deterministic_pipeline_version

ClassificationContractId =
    opaque identifier owned by agent-service
    # internally derived from classification pipeline/model/taxonomy contract

ClassificationKey =
    analysis_id
  + classification_contract_id

AssembledAnalysisKey =
    DeterministicAnalysisKey
  + ClassificationKey

AgentReviewSpecKey =
    repository_key
  + commit_sha
  + review_goal
  + agent_version
  + prompt_version
  + model_profile

AgentContextFingerprint =
    classification_result_id
  + retrieval_index_version
  + taxonomy_version
  + graph_snapshot_version   # NONE when GraphRAG is degraded

AgentResultCacheKey =
    hash(AgentReviewSpecKey + AgentContextFingerprint)

agent_run_id = UUID  # always unique; never the cache key
```

**Freshness is intentionally split: a deterministic analyzer change or source SHA change triggers repository re-analysis; a classifier/model/taxonomy change triggers re-classification only. A completed deterministic result remains valid while its assembled AI classification may become pending.**

## 2.2a Classification contract ownership and invalidation

```
ClassificationContract  [owned by agent-service]
{
  classification_contract_id     # opaque outside agent-service
  classification_pipeline_version
  classification_model_profile
  prompt_version
  taxonomy_version
  created_at
  effective_from
}

Authority rule:
- agent-service owns classifier/model/pipeline version semantics.
- agent-service consumes governance taxonomy.changed events.
- when its effective classification contract changes, agent-service publishes
  classification.contract.changed.
- repository-service stores a local projection of only the current opaque
  classification_contract_id; it does not reconstruct the ID from fields it does not own.
- on startup/missed-event suspicion, repository-service reconciles through
  GET /internal/v1/classification-contract/current.

Taxonomy fan-out decision:
A global taxonomy change may create a new ClassificationContractId for the corpus,
but there is NO eager corpus-wide reclassification. Existing analyses are lazily
reclassified when accessed. Background sweeping is optional later and disabled in
the zero-cost profile.
```

## 2.3 Error model

| **Class**              | **Examples**                                            | **Default handling**                                |
| ---------------------- | ------------------------------------------------------- | --------------------------------------------------- |
| **VALIDATION**         | Bad URL, unsupported provider, invalid review input     | Reject without retry.                               |
| **AUTHORIZATION**      | Missing/insufficient privilege                          | Reject; audit sensitive attempts.                   |
| **NOT_FOUND**          | Repository/version/run absent                           | Return not found.                                   |
| **TRANSIENT_EXTERNAL** | GitHub timeout, Gemini 429/5xx, Neo4j transient failure | Bounded exponential retry with jitter.              |
| **PERMANENT_EXTERNAL** | Repository deleted/private without access               | Fail job with actionable reason.                    |
| **CONFLICT**           | Duplicate active analysis / already-decided review      | Return existing resource or conflict state.         |
| **POLICY**             | Tool/write operation not allowed                        | Block; optionally require governance/HITL.          |
| **BUDGET**             | Agent step/token/cost budget exceeded                   | Stop with partial/failed status; preserve evidence. |
| **INTERNAL**           | Unexpected invariant violation                          | Fail safely; trace with correlation ID.             |

## 2.4 Transactional event publication

Any service that must persist canonical MongoDB state and publish a Kafka event uses a transactional outbox.

```
Mongo transaction
    ├─ write/update domain document
    └─ insert outbox_event

COMMIT
   ↓
OutboxPublisher
   ↓
Kafka
   ↓
mark outbox_event PUBLISHED

If publisher crashes:
unpublished outbox rows are retried.

Consumers are idempotent using event_id + consumer identity.
```

## 4.5 Concurrency / single-flight algorithm

1. Taxonomy/classifier contract changes do not eagerly sweep the corpus. Lazy access triggers reclassification; optional background refresh is a later cost-controlled job.
2. An assembled READY result is cacheable only under AssembledAnalysisKey containing the currently applied ClassificationKey.
3. When classification callback arrives, repository-service verifies the callback contract/key is still desired. Matching results are installed; stale results are acknowledged as SUPERSEDED and never become current ai_enrichment.
4. Trigger or attach to classification by POST /internal/v1/classification-runs {analysis_id, expected_contract_id}. The agent endpoint is idempotent and returns the existing run for the same ClassificationKey if present.
5. If classification is stale, atomically set product_status = AI_CLASSIFICATION_PENDING and desired_classification_contract_id = current contract.
6. If applied_classification_contract_id equals current ClassificationContractId and applied_classification_key equals desired ClassificationKey, the assembled result is current and may be served/cached.
7. Compute desired ClassificationKey = analysis_id + current ClassificationContractId. repository-service does not derive pipeline/model/taxonomy values itself.
8. For an existing deterministic result, read the locally projected current ClassificationContractId advertised by agent-service. If the projection is absent or reconciliation is required, call GET /internal/v1/classification-contract/current and update the local projection.
9. On deterministic completion, persist result + outbox event transactionally. repository.analysis.deterministic.completed triggers the normal automatic classification path in agent-service.
10. If no deterministic result exists, atomically create/claim analysis_jobs by DeterministicAnalysisKey. A unique index guarantees one deterministic owner across pods; duplicate callers attach to the existing job.
11. Compute DeterministicAnalysisKey = repository_key + commit_sha + deterministic_pipeline_version.
12. Resolve canonical repository_key and current commit_sha.

## 5.3a Automatic Classification Workflow

**Classification is automatic and bounded. It is triggered by repository.analysis.deterministic.completed or by classification-freshness invalidation; it is not a LangGraph architecture-review run.**

```
ClassificationContract  [agent-service authority]
  classification_contract_id = opaque
  pipeline/model/taxonomy metadata = informational to other services

Triggers:
A. Normal new deterministic analysis
   repository.analysis.deterministic.completed (Kafka)

B. Lazy stale-on-read invalidation
   POST /internal/v1/classification-runs
   { analysis_id, expected_contract_id }

ClassificationRun
{
  classification_run_id
  analysis_id
  classification_contract_id
  classification_key = analysis_id + classification_contract_id
  status  # QUEUED/RUNNING/VALIDATING/COMPLETED/DEGRADED/FAILED/SUPERSEDED
  outputs + evidence/provenance
}

Flow:
start/attach by ClassificationKey
  → read deterministic facts/evidence via repository API
  → use taxonomy version embedded in/current for the contract
  → Gemini structured classification
  → validate
  → POST idempotent result to repository-service
  → if repository accepts as current: publish classification.completed/degraded (advisory)
  → if repository reports stale: mark SUPERSEDED and publish classification.superseded

repository.analysis.ready, emitted by repository-service after install, is the
authoritative signal that the assembled RepositoryAnalysis is current.
```

## 6.4 Graph projection rules

- Only consume committed analysis/taxonomy events; graph projection is idempotent by event_id.
- RepositoryVersion nodes are immutable by commit SHA; latest/current flags may move but history is preserved.
- TechnologyUsage is version-specific. Removing a technology in a new version does not delete historical usage from prior versions.
- Canonical role/taxonomy changes arrive from Governance events; Graph Intelligence does not invent canonical IDs.
- CO_OCCURS_WITH is derived from repository-version usage and can be recomputed; it is never treated as source truth.

## 6.4a Graph projection watermark contract

```
GraphContext {
  graph_snapshot_version
  latest_processed_event_id
  taxonomy_version
  repository_projection_sha
  projection_status   # CURRENT | LAGGING | UNAVAILABLE
  context
}

Architecture-review rule:
CURRENT   → GraphRAG may contribute and graph_snapshot_version enters AgentContextFingerprint.
LAGGING   → review degrades to repository evidence + Hybrid RAG; graph_snapshot_version = NONE.
UNAVAILABLE → same degraded behavior.

A later current run therefore cannot collide with an earlier degraded cached result.
```

## 8.3 Delivery semantics

- Kafka delivery is treated as at-least-once; all consumers are idempotent.
- Outbox pattern protects Mongo-state-to-Kafka publication.
- event_id identifies one logical event; consumers record or derive dedupe state.
- Consumers must tolerate duplicate and delayed events.
- Ordering is guaranteed only within a partition. Repository lifecycle events use repository_key for ordering.
- Schema evolution is additive by default; breaking changes require event_version increment and dual-reader/transition plan.
- Cross-topic ordering is not assumed. Consumers use aggregate IDs, keys, status and idempotency rather than relying on temporal delivery order.
- repository.analysis.ready is the authoritative signal that the assembled RepositoryAnalysis has current installed AI classification. Consumers that require current assembled state must wait for/use analysis.ready rather than classification.completed.
- classification.completed/degraded is an advisory classifier-workflow signal and is emitted only after repository-service accepts the callback as current. classification.superseded is emitted when the callback is no longer current.

| **Clone/fetch repository**                  | Yes, transient only               | Workspace scoped by deterministic job/attempt; cleanup prior partial workspace.       |
| **Persist deterministic analysis**          | No blind retry after uncertainty  | Upsert/unique DeterministicAnalysisKey; transaction.                                  |
| **Consume classification.contract.changed** | Yes                               | Idempotent repository-local projection update by event_id/contract_id.                |
| **Reconcile classification contract**       | Yes, transient                    | GET current contract from agent-service; does not mutate classifier authority.        |
| **Trigger ClassificationRun**               | Safe retry                        | POST is idempotent by ClassificationKey = analysis_id + contract_id.                  |
| **Apply classification callback**           | Safe retry                        | Idempotent by result ID; install only if contract/key still desired; else SUPERSEDED. |
| **Publish Kafka event**                     | Yes via outbox                    | event_id stable across retries.                                                       |
| **Consume Kafka event**                     | Yes                               | Consumer dedupe + idempotent projection.                                              |
| **Neo4j projection**                        | Yes                               | MERGE/upsert stable IDs; event_id dedupe.                                             |
| **Gemini call**                             | Bounded transient retry           | Run/step identity; duplicate generation cannot duplicate side effects.                |
| **Governance decision**                     | No duplicate semantic application | Review status + transaction + unique decision rule.                                   |
| **GCS/artifact write**                      | Yes                               | Versioned deterministic object path.                                                  |
| **Redis cache**                             | Best effort                       | Never required for correctness.                                                       |

# 15\. Repository Difference Model

For the four lifecycle scenarios, LLD distinguishes three deltas:

| **Delta**            | **Definition**                                                               | **Primary reaction**                                                              |
| -------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **SOURCE_DELTA**     | Commit SHA changed / files changed                                           | New repository version and analysis.                                              |
| **FEATURE_DELTA**    | Behavior/code evidence changed but effective technology usage remains stable | Refresh changed evidence; retain technology set; architecture/history may change. |
| **TECHNOLOGY_DELTA** | Technology usage added, removed, replaced or contextual role changed         | Versioned TechnologyUsage update, graph projection update, discovery checks.      |

The exact changed-file/diff algorithm is implemented behind a RepositoryDiffService. A full re-analysis is always a correctness fallback; incremental reuse is an optimization.

# 19\. Finalized Decisions Added During LLD Review

| **Decision**                         | **Final LLD architecture**                                                                                                                                     |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Basic AI classification**          | Automatic bounded ClassificationRun inside agent-service; not repository job and not architecture-review LangGraph.                                            |
| **Canonical key vocabulary**         | DeterministicAnalysisKey, ClassificationContractId, ClassificationKey, AssembledAnalysisKey, AgentReviewSpecKey, AgentContextFingerprint, AgentResultCacheKey. |
| **Classification authority**         | agent-service owns ClassificationContractId and its pipeline/model/taxonomy composition; repository-service treats it as opaque.                               |
| **Contract propagation**             | agent-service publishes classification.contract.changed; repository-service stores a local projection and reconciles through GET current contract.             |
| **Freshness invalidation transport** | New deterministic analysis: Kafka deterministic.completed. Lazy stale-on-read: idempotent POST /internal/v1/classification-runs.                               |
| **Classification invalidation**      | Contract change re-runs classification only; no repository clone/re-analysis.                                                                                  |
| **Taxonomy fan-out**                 | Global contract change is accepted but refresh is lazy; no eager corpus sweep. Background refresh is later/cost-controlled.                                    |
| **Stale classification result**      | Never installed; repository returns SUPERSEDED and agent marks run accordingly.                                                                                |
| **Completion semantics**             | classification.completed/degraded is advisory after callback acceptance; repository.analysis.ready is authoritative assembled-current signal.                  |
| **Architecture-review identity**     | AgentReviewSpecKey + AgentContextFingerprint → AgentResultCacheKey.                                                                                            |
| **Graph consistency**                | Graph context determining; watermark/NONE enters identity; lag/unavailable degrades gracefully.                                                                |
| **RLHF/post-training**               | LATER offline plane; no V1 request-path dependency.                                                                                                            |
| **Training source invariant**        | Only explicit immutable training snapshots + eligible preferences; correction ledger never direct source; snapshot creation cannot be automatic 1:1 mirroring. |
| **Learning bounded context**         | Separate LATER learning-control-service; governance-service remains product/ontology governance.                                                               |
| **Infrastructure cost**              | Local/portfolio profile must run without paid managed infrastructure; production topology remains logically equivalent through adapters.                       |

## 21.3 Cost-control rules

- Production architecture may use managed services without changing core domain code because infrastructure is behind ports/adapters.
- Flink, Spark, vLLM and RLHF training remain on-demand LATER workloads rather than always-running infrastructure.
- Private/proprietary repositories are not sent to third-party free model APIs by default; use mock/local model or an explicitly approved paid/private path.
- No background corpus-wide reclassification is enabled in the zero-cost profile; taxonomy/classifier contract invalidation is lazy on access.
- FREE-CLOUD is best-effort, not a guarantee of \$0: quotas/pricing can change and usage must be capped.
- LOCAL / PORTFOLIO is the default and must be able to exercise the complete V1 logical flow without a recurring cloud bill.
